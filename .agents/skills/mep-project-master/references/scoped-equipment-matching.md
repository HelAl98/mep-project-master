# Scoped unreviewed equipment matching

This optional operation runs the existing native matcher once on an exact audited current dataset. It does not change full Stage03–05 states, complete Stage06, start downstream stages, merge confirmed physical identities, or create technical approvals. Default workflow prerequisites remain unchanged.

Use scripts/master.py --config <project> matching-scope --receipt <path> to audit a mep-matching-scope/1 receipt in the existing master_operator_events table. Required standard envelope: project_id,scope_id,actor,reason,engineering_approval=false. Required fields: operation=06:mep-equipment-matcher.match, full_source_coverage=false, technical_findings_promoted=false, limitations, context_limitation_ids, matching_config {path,sha256}, equipment_scope_id, allowed_disciplines, imports and dataset_fingerprint. Human source-limit acceptance must explicitly allow this matching operation; append new acceptance rather than altering previous receipts.

matching_scope.dataset returns exact current import identities (import_id,file_id,sha256,analysis_id,role,slot), the raw current occurrence/parameter/review digest, imports and occurrences. Receipts pin all of these, the current equipment source/provenance audit and the matching configuration. Current means latest per original file/slot and registry analysis. Because the native matcher has no source/system filter, ANY extra or missing active source or mismatched role/slot/config blocks execution. Original live/archive and derived evidence hashes are checked by existing equipment-scope validators. All current inputs must remain unreviewed/needs_review and within the allowed discipline set. Changed sources, reviews, configurations, imports or retired limitations invalidate eligibility. Partial imports retain their exact native issues and are not promoted to complete coverage.

A request identifies project_id,scope_id,operation,receipt_id. A single-job plan has the standard envelope, prior_run_ids, job and result_path. job has a unique id, skill=mep-equipment-matcher, command=match, exact source_file_ids, inputs=[], options={}, and scoped_request path. matching-execute --plan <path> verifies current Stage01/02 and exact scope, then uses the existing master run_job/adapter/native matcher under the project lock. It checks the actual persisted native run and unchanged input digest. The scope is single-use; it does not authorize a second matching run. Native import config consistency remains mandatory; changed category config requires incremental refresh using existing source packages, not new extraction.

Native probable/possible proposals remain unreviewed. FCU type-bearing occurrences are not individual technical types or installed quantities. Group quantities remain separate from confirmed instances. Exact tags may propose correspondence across occurrences, including repeated annotations within one document; report those separately from cross-document proposals. No tag aliases or proximity-based identity are implied by this mechanism.

The native matcher can report global registered-source processing warnings even though its occurrence dataset is scoped. Retain those raw warnings, label outside-scope inventory warnings separately, and do not interpret them as proof of missing HVAC equipment. Native limits remain in effect; report truncation if a candidate-pair/association limit is reached. Do not run group, approvals, Stage07 or any downstream operation through this matching-only plan. No specialized skill, matching algorithm, SQLite schema or agent route is changed.
