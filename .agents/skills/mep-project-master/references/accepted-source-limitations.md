# Accepted source limitations and exact-operation eligibility

This optional contract keeps the eleven stages and existing SQLite schema. Full stage statuses and checkpoints retain their original meaning. A separately audited available-evidence scope can make one supported operation eligible while Stage03/04 remain BLOCKED. It cannot approve engineering, promote findings, suppress issues, or exempt the project from coverage, QC, lineage or revision gates. No additional agent or model route is introduced.

## Commands and audit contracts

Use the existing `scripts/master.py --config <absolute-project-config>` prefix. Relative paths resolve against that configuration. Each receipt has project_id, scope_id, actor, reason and engineering_approval=false. The supplied actor is an attribution, not authenticated authority.

- `source-limitation --receipt <file> --human-authorized`: only after an actual human supplies the continuation decision. Schema `mep-accepted-source-limitation/1`, disposition `accepted_unavailable`, classification `unresolved_source_coverage_limitation`, authorization evidence, allowed_operations and references. Each reference identifies name, exact registered host file_id/sha256, potentially_affected_information and unresolved_coordination_limitations. Do not infer discipline from filename alone or label absence a confirmed design conflict. Host identity and live/archive bytes must match the selected scope. Receipt and accepted state are append-only audited in existing master_operator_events.
- The same command with disposition `retired` and limitation_id appends retirement; it does not edit/delete the original acceptance. Restoration/new evidence requires retirement/reassessment, registration and new receipts, never automatic engineering approval.
- `available-evidence --receipt <file>`: schema `mep-available-evidence/1`, stage `03` or `04`, allowed_operation, full_source_coverage=false, technical_findings_promoted=false, limitations, items, optional context_limitation_ids. Each item identifies original {file_id,sha256}, evidence {path,sha256}, conversion {path,sha256}, available_scope=`native_pdf_text_only`, requires_external_references=[] and warning_disposition. Stage04 also supplies parent_receipt_id and each item's parent_evidence_sha256. The explicit DOC-to-PDF provenance is checked rather than equating original and conversion hashes. Receipts and evidence must remain in the project's output directory. No source conversion/extraction is performed by this command.
- warning_disposition requires inventory_digest (common.key over package issues followed by each record's review.issues in record order), action=`preserve_unreviewed_for_text_extraction_or_ingestion`, and reason. Only raster_content_unprocessed, unicode_text_review, specification_layout_review and continuation_candidate can be retained for this restricted native-text operation. Unknown/material warnings block. Image content and Unicode/paragraph interpretation remain unverified. Existing ETL package validation still rejects approved extraction records, invalid locators and malformed evidence. Exact Stage04 fragments must match indexed native Stage03 lines and locators.
- `eligibility --request <file>` checks an explicit {project_id,scope_id,operation,receipt_id,evidence:[{file_id,path,sha256}]} subset. Supported operations only: `04:specification-extractor.extract` from Stage03 available text, and `05:etl-pipeline.ingest` from Stage04 exact fragments. Eligibility is a current read-only calculation, not a COMPLETED event, execution receipt, technical readiness decision or an import. Check eligible=true explicitly; a negative assessment returns its reason.

For normal master execution, configure exact source_file_ids and inputs plus scoped_request on each selected Stage04/05 job. The request operation must match the stage/skill/command, all paths and IDs must match its audited subset, and Stage01/02 must be current COMPLETED. Each existing ETL job takes one package, so use a one-package request per job. A many-package request is useful for readiness assessment but is not one ETL invocation. Cached operations are rechecked. This only bridges the immediate blocked Stage03 or Stage04 dependency; it does not waive coverage() or any other prerequisite. Execution can preserve successful operations while full stage completion remains BLOCKED until the original coverage contract is met. Do not label scoped execution full stage completion. Existing warning-bearing extraction jobs retain the strict original result validator; reuse available extraction receipts instead of repeating them.

## Invalidation and boundaries

Audits retain the full current source inventory digest and registry heads. Any new/restored/changed source inside the registered project tree, changed registry head, changed receipt, changed source/conversion/package hash, missing original archive or retirement fails eligibility and invalidates dependent scoped jobs. This conservative invalidation can include unrelated source changes; reassess rather than silently carrying acceptance forward. Routine source hashing is not an external-Xref path search. The master never probes missing external paths. If an external reference is restored outside the registered tree, the operator must register it and retire/reassess the affected limitation before use. Previously written conclusions remain historical; their eligibility is no longer current. No technical approval is inferred or automatically revoked/replaced by an eligibility result.

The first contract supports existing native PDF text and exact specification fragments only. It does not declare CAD extraction complete, repair missing Xrefs, validate raster content, certify Word rendering fidelity, resolve Unicode interpretation, approve five-digit section interpretation, reconcile equipment, or authorize downstream design/coordination conclusions. Context limitations travel with eligible inputs but are not exemptions for those inputs. Exact quoted text is available; technical correctness/applicability remains pending.

## Compatible master implementation upgrade

The master code fingerprint deliberately invalidates old task caches. An operator may capture a `mep-prerequisite-revalidation/1` baseline before a compatible master-only upgrade and use `revalidate-prerequisites --receipt <file>` after it. This is limited to existing completed Stage01/02 events and exact unchanged configurations, job specifications, live-source inventory/registry heads, specialized-skill signatures, input hashes, persisted references and output hashes. All checks precede writes. New completion events reference the old events and immutable baseline; originals are retained. This is an operational implementation revalidation, not rerunning extraction or approving engineering. Changed inputs require normal reassessment, not editing the baseline to make it pass. Preserve the baseline alongside the upgrade backup and synchronization manifest.

No migrations, new engineering tables, general exclusion statuses, technical-review writes, native specialist changes or model routing changes are needed. Installation receives static validation only unless separately authorized. Real project receipt registration/eligibility reassessment is actual requested work, not a test pipeline.
